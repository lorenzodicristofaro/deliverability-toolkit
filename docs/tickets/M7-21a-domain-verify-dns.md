Maintainer decision 2026-11-17: domains must have ownership verification; preferred method DNS TXT, alternative email (M7-21b). SPEC.md section 3 records it. Unverified domains stay addable and usable with DNS-based checks; http_fetch (any run path) and scheduled monitoring of such checks need a verified domain. This closes the medium M7-02 follow-up on http_fetch reading arbitrary public hosts.
Acceptance criteria:
- Model + migration: domain gets verification state (status unverified|verified, verified_at, method (dns_txt now, email later), token stored hashed or token with expiry, token_expires_at). Migration is the next revision after 0014; existing domains migrate as unverified; downgrade is clean. SQLite and PostgreSQL both covered.
- Start (owner/admin): the server issues a random token with the `secrets` module (>= 128 bits), shown once with the exact record to publish (TXT at `_dt-verify.<domain>`, value `dt-verify=<token>`). Only a hash is stored if the token is not needed again; otherwise the token is stored with expiry and never logged. Expiry is a bounded setting (min and max enforced, default stated in docs/SETUP.md). Re-issue invalidates the previous token.
- Verify now: TXT lookup at `_dt-verify.<domain>` through the existing resolver path (app/dns, no new network code); match is exact after joining the character-strings of each TXT record, compared in constant time; token expired -> not verified, user told to restart. Outcomes: match -> verified (verified_at, method dns_txt, token cleared); wrong token or no matching record, nxdomain, nodata -> not verified yet (no state change except a last_checked note if added); DNS failure (timeout, servfail, refused) -> `error` outcome, never verified, never swallowed, user-visible message.
- Rename: the update service allows renaming a domain (app/api/v1/domains.py update_domain). A rename resets verification to unverified and clears the token (state this in the docs and test it).
- Gate: http_fetch custom checks (run, dry run POST /custom-checks/test, and any definition targeting the domain) return Check status `error` with reason `domain_unverified` for an unverified domain, before any fetch is attempted; DNS-based checks are unaffected. The scheduler/monitor path must not schedule http_fetch for an unverified domain (document the hook if the monitoring tickets are not merged yet; do not leave it silently open).
- Permissions: new action `domain.verify` = owner, admin, resource DomainResource; per-user deniable like the other actions; analyst and client viewer denied. Tests per endpoint: cross-tenant 404, client viewer denied (403/404 per existing convention), analyst denied, per-user deny, CSRF on the web forms and state-changing API calls.
- API endpoints (start, verify, read status) + minimal web UI on the domain page: status badge (unverified/verified/error), start and verify buttons, instructions showing record name and value, i18n en + it. The token is shown once on the start response only; never in logs, URLs or other pages.
- Audit entry for start/verified if the audit mechanism exists; if not (domains.py carries TODO(M10)), add the matching TODO line and no new mechanism.
- Periodic re-verification is a follow-up unless trivial; record the follow-up in TODO.md.
- Tests table-driven with a fake resolver, no network: match, wrong token, expired token, multi-string TXT (token split across strings), multiple TXT records at the name, DNS error, nxdomain, nodata, re-issue invalidates old token, rename resets.
